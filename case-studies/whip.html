01

项目背景与挑战Context

WHIP 围绕日常健康记录展开：饮食、饮水、运动、身体状态与睡眠频率不同，却需要在同一天被查看。目标用户设定为希望自己保管记录、愿意持续输入日常信息的个人用户。

设计假设是：降低每次录入的步骤，比在首屏堆积更多指标更有价值。因此先把入口安排成今日、饮食、运动、趋势与我的五个模块，再让今日页承担记录入口和当天摘要。

01 / CAPTURE随手录入
02 / STORE保存在设备
03 / REVIEW按日期回看
04 / RECOVER备份与恢复

把空白状态也当作正式界面

新用户的健康空间不预置示例记录。没有录入时显示“等待第一条记录”与明确的行动入口；未知营养数据保留为空值。这样既避免虚构用户状态，也使第一次操作的下一步足够清楚。

我的工作是借助 AI 工具完成产品页面与功能开发，并核对关键计算和保存逻辑。这里呈现的是个人项目实现，不将设计假设写成已经完成的用户研究。

03

核心交互与状态Key interactions

与财富 Pro 的 Canvas 扇区不同，WHIP 的饮水圆盘使用 SVG。这个组件只需要表达一个记录值与目标值的比例，SVG 能用更少的状态保持图形与可访问文本一致。

从比例到弧长

设记录饮水量为 a，目标为 t，比例 p = a / t。圆周长为 2πr；采用 pathLength="100" 后，可以直接把弧长写成百分比。绘制值封顶 100%，文字仍可保留实际比例。

p = t > 0 ? a / t : 0
L = 2πr
pathLength = 100
strokeDasharray = min(100, p × 100) + " 100"
WaterDisc.tsx 的图形半径为 50，内部次级圆为 39。圆盘使用 progressbar 语义，向辅助技术提供实际毫升数与目标。

把“保存成功”放在反馈之前

记录数据先进入 repository，再写入 IndexedDB。界面通过 useLiveQuery 订阅变化，使今日摘要与记录列表从同一份保存结果更新。启动时若本地数据库不可访问，应用显示重试信息，不把失败包装成成功。

中断后的状态要能够解释

初始化会把仍标记为 active 的运动记录转换为 paused，并保留可用的更新时间。这样，重新打开后不会把关闭页面期间的时间悄悄算成持续运动。

先解决断网记录，再界定同步边界

离线写入直接发生在本地数据库，不需要排队上传。Service Worker 负责应用壳缓存；它解决“页面能否打开”，不负责多端数据冲突。当前项目没有自动跨设备同步。更换设备需要导出与恢复，不能把这条路径描述为“断网重连后自动同步”。

选择解决的任务权衡与边界
IndexedDB结构化记录、索引与事务数据跟随浏览器来源，需考虑容量、清理与备份
JSON 恢复记录迁移与误操作后的恢复路径合并按 ID 跳过已存在记录，不等于双向冲突合并
应用壳缓存缓存就绪后离线打开核心页面首次访问仍需联网；天气与可选模型有独立网络依赖

恢复是一组原子操作

导入先校验数据结构，再用跨表读写事务进行替换或合并。合并时通过 bulkGet 查重，只写入不存在的 ID；替换由界面要求明确确认。非法导入不会作为部分成功写入数据库。

本地优先减少了默认上传健康记录的需求，但不等同于端到端加密。设备丢失、站点数据清理与浏览器存储策略仍是需要面对的风险，因此备份入口属于核心能力。
